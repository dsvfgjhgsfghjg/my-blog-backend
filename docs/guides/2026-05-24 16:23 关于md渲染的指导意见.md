# 关于 Markdown 代码块渲染问题的根因分析与修复建议

## 🔍 问题现象

文章内容中的代码块被渲染为普通段落（`<p>` + `<br>`），而不是带语法高亮的代码块（`<pre><code>`）。

例如原本的 Markdown 代码块：
```bash
docker run -d \
  --name gitea-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitea/act_runner:latest
```

被渲染成了：
```html
<p>
  docker run -d<br>
  --name gitea-runner<br>
  -v /var/run/docker.sock:/var/run/docker.sock<br>
  gitea/act_runner:latest
</p>
```

## 🧪 前端渲染链路排查

### 前端渲染流程

```
后端返回 content (原始Markdown文本)
  → ArticleRenderer.vue (v-html="renderedContent")
    → markdownRenderer.ts (markdown-it 解析 + 代码高亮)
      → DOMPurify 清洗
        → 输出安全HTML
```

### 前端已排查通过项

| 检查项 | 结果 |
|--------|------|
| `markdownRenderer.ts` `highlight` 函数 | ✅ 有完整的语言检测 + 默认 fallback（escapeHtml） |
| DOMPurify `ALLOWED_TAGS` 包含 `pre`, `code` | ✅ 已允许 |
| DOMPurify `ALLOWED_ATTR` 包含 `class` | ✅ 已允许 |
| `codeHighlighter.ts` 注册的语言 | ⚠️ 缺少 `kotlin`（已修复，见下文） |

### 前端结论

前端渲染逻辑是**正确**的。`markdownRenderer.ts` 中的 `highlight` 函数 **始终** 返回 `<pre><code>` 结构：

```typescript
highlight: function (str: string, lang: string): string {
    if (lang && hljs.getLanguage(lang)) {
      // 支持的语言 → 高亮渲染
      return `<pre class="hljs"><code class="language-${lang}">...</code></pre>`
    }
    // 不支持的语言 → 转义后正常显示
    return `<pre class="hljs"><code>${md.utils.escapeHtml(str)}</code></pre>`
}
```

这意味着：**只要后端返回的是原始 Markdown 文本（含正确的代码块标记），前端就能正确渲染。**

## 🎯 根因分析（后端正解）

问题几乎可以确定发生在**后端的 Jsoup XSS 过滤环节**。

### 可能的故障场景

#### 场景 A：Jsoup 清洗损坏了代码块标记（最可能）

如果后端对原始 Markdown 文本直接使用 `Jsoup.clean()` 做 XSS 过滤（而不是对最终 HTML 做过滤），会导致：

```
原始 Markdown 文本：
```bash
docker run ...
```

Jsoup.clean(原始文本, Safelist) → Jsoup 是 HTML 解析器，不理解 Markdown 语法
→ 反引号（```）被当做普通文本处理
→ 在 Jsoup 重构输出时，可能丢失代码块结构
→ 存储到 MinIO 的内容已损坏
```

**Jsoup 设计用于解析和清理 HTML，不是 Markdown。** 对 Markdown 文本运行 Jsoup.clean() 会导致：
- 反引号（`）被当成普通字符
- 换行符可能被标准化
- 输出文本的结构可能发生变化

#### 场景 B：后端进行了 Markdown→HTML 预转换

如果后端流程是：
```
Markdown → 转 HTML → Jsoup.clean(HTML) → 存储清理后的HTML（而不是原始Markdown）
```

而 HTML 转换器（非 markdown-it）对代码块的处理不完善（例如代码块变成了 `<p>` + `<br>`），则前端收到的内容已经是损坏的 HTML，`markdown-it` 无法再正确解析。

### 判断方法

找一篇渲染有问题的文章，打印后端返回的 `content` 字段原始值，检查：

1. 代码块标记（```）是否还存在？
2. 如果代码块标记消失，但出现了 `<br>` 或 `<p>` 标签 → 场景 B
3. 如果代码块标记消失，内容变成纯文本（无标签）→ 场景 A

## 🔧 修复建议

### 方案一：后端 Jsoup 只过滤最终 HTML，不碰 Markdown（推荐）⭐⭐⭐⭐⭐

**核心原则：Jsoup 不应处理原始 Markdown 文本。**

正确的 XSS 防护链路：
```
用户输入 Markdown → 存储原始 Markdown 到 MinIO → 响应时直接返回原始 Markdown
                                                      ↓
后端不在存储环节做 Jsoup 过滤                    前端 markdown-it 渲染
                                                      ↓
                                                  DOMPurify 只清洗最终 HTML ✅
```

**修改建议：**
- 移除创建/更新文章时对 `content` 字段的 Jsoup 过滤
- XSS 过滤交给前端 DOMPurify 完成（前端已正确配置）
- 如果仍需后端过滤，应在 **Markdown 被渲染成 HTML 之后**（例如在预览接口中）才应用 Jsoup

### 方案二：如果必须在后端做 Jsoup 过滤

Jsoup 只对**真的 HTML 标签生效**，不改动 Markdown 语法。如果确实需要过滤，确保两点：

1. **Jsoup 配置要宽松，允许内容中存在反引号等特殊字符**
2. **确认过滤后的内容仍然是有效的 Markdown 格式**

示例配置：
```java
// 用于 Markdown 的安全配置（仅移除脚本等危险内容）
Safelist markdownSafeList = Safelist.none()
    // 不添加任何 HTML 标签（不需要对 Markdown 做 HTML 级别的过滤）
    ;

// 清理时仅移除 HTML 标签，保留 Markdown 语法
String cleaned = Jsoup.clean(originalContent, markdownSafeList);
// Jsoup.clean() 会剥离 HTML 标签，但 Markdown 文本应被保留
```

### 方案三：纯文本内容不做 Jsoup 过滤

对于包含代码块的文章，最安全的做法是：

```java
// 对于 Markdown 内容（不含 HTML 标签），不做 Jsoup 转换
if (!content.contains("<")) {
    // 纯 Markdown 文本，跳过 Jsoup
    return content;
}
// 只对含 HTML 标签的内容做过滤
return Jsoup.clean(content, safelist);
```

## 🛡️ XSS 防护方案（对后端的完整提示）

### 核心问题：去掉 Jsoup 后 XSS 怎么办？

**方案一** 建议后端移除对 Markdown 原始文本的 Jsoup 过滤，一个自然的疑问是：**XSS 谁来防？**

答案是：**前端 DOMPurify 已经是正确且完善的 XSS 防线**。后端 Jsoup 对原始 Markdown 做过滤反而是"越级操作"，不仅破坏了 Markdown 语法，也没有提供额外的安全价值。

### 推荐的 Markdown 架构下的 XSS 防护链路

```
┌──────────────────────────────────────────────────────────────┐
│                   正确的 XSS 防护链路                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  用户提交 Markdown                                            │
│     ↓                                                        │
│  后端：存储原始 Markdown 到 MinIO（不做任何 Jsoup 过滤）       │
│     ↓                                                        │
│  后端：返回原始 Markdown 给前端                                │
│     ↓                                                        │
│  前端 markdown-it：Markdown → HTML（生成 <pre><code> 等）     │
│     ↓                                                        │
│  前端 DOMPurify：白名单清洗 HTML（移除所有危险标签和属性）     │
│     ↓                                                        │
│  前端 v-html：渲染安全 HTML 到页面                            │
│     ↓                                                        │
│  浏览器：CSP HTTP 头（第二道防线，进一步限制）                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**关键原则：XSS 过滤应当作用于"渲染后的 HTML"，而不是"原始 Markdown 文本"。**

### 前端 DOMPurify 当前覆盖情况

你的前端已经在 `markdownRenderer.ts` 中使用 DOMPurify 进行了白名单清洗，覆盖了以下所有攻击向量：

| 攻击向量 | DOMPurify 处理方式 | 是否覆盖 |
|----------|-------------------|---------|
| `<script>` 标签注入 | 白名单中无 `script` → 自动移除 | ✅ |
| `onerror`/`onclick` 事件处理器 | `ALLOWED_ATTR` 白名单无 `on*` 属性 → 自动移除 | ✅ |
| `javascript:` 协议链接 | DOMPurify 默认过滤危险 URI 协议 | ✅ |
| `data:` URI 注入 | 仅允许 `http/https` → 自动拦截 | ✅ |
| CSS `expression()` | DOMPurify 默认移除 | ✅ |
| `<iframe>`/`<object>` 嵌入 | 白名单中无这些标签 → 自动移除 | ✅ |
| 大小写绕过 (`<ScRiPt>`) | DOMPurify 自动标准化标签 → 正常移除 | ✅ |
| Unicode 编码绕过 | DOMPurify 自动解码 → 正常移除 | ✅ |
| HTML 实体编码绕过 | DOMPurify 自动解码 → 正常移除 | ✅ |
| SVG `<use>` 注入 | 白名单中无 SVG 相关标签 → 自动移除 | ✅ |
| `<base>` 标签劫持 | 白名单中无 `base` → 自动移除 | ✅ |
| `<form>` 表单劫持 | 白名单中无 `form` → 自动移除 | ✅ |

**结论：前端 DOMPurify 配置已经覆盖了所有常见的 XSS 攻击向量，移除后端 Jsoup 对 Markdown 的过滤不会导致安全缺口。**

### 后端需要做的代码修改

#### 1. 文章创建/更新接口 — 移除对 `content` 字段的 Jsoup 过滤

找到 `PostServiceImpl.java`（或类似的服务类），在创建和更新文章的方法中，**跳过对 `content` 字段的 Jsoup.clean() 调用**。

**修改前（猜测的当前代码）：**
```java
// 对 content 做 Jsoup 过滤（破坏 Markdown 语法）
String safeContent = Jsoup.clean(postRequest.getContent(), POST_CONTENT_SAFELIST);
// 然后存储 safeContent 到 MinIO
minioService.uploadContent(postId + "/" + uuid + ".md", safeContent);
```

**修改后（推荐）：**
```java
// 不对 Markdown 内容做任何过滤，直接存储原始 Markdown
String originalContent = postRequest.getContent();
// 直接存储原始内容到 MinIO
minioService.uploadContent(postId + "/" + uuid + ".md", originalContent);
```

#### 2. 其他纯文本字段仍可保留 Jsoup 过滤（可选，推荐保留）

对于**非 Markdown 字段**（如标题 `title`、摘要 `summary`、分类名称等纯文本字段），Jsoup 过滤或 HTML 转义仍然是合理的安全措施：

```java
// 标题等纯文本字段：可以安全地使用 Jsoup 过滤或 Hutool 转义
String safeTitle = HtmlUtil.escape(postRequest.getTitle());  // 使用 Hutool
// 或者
String safeTitle = Jsoup.clean(postRequest.getTitle(), Safelist.none());
```

**为什么这些字段可以过滤：** 标题、摘要等字段不是 Markdown 格式，它们通常是纯文本或少量 HTML，Jsoup 过滤不会破坏语法结构。

#### 3. 评论内容的 XSS 防护（独立处理）

评论内容与文章内容不同，评论通常是纯文本或简单富文本，可以用更严格的规则：

```java
// 评论的 Jsoup Safelist 示例（仅允许极少数标签）
Safelist COMMENT_SAFELIST = Safelist.none()
    .addTags("strong", "em", "code", "br");
// 对评论内容使用 Jsoup 过滤
String safeComment = Jsoup.clean(commentContent, COMMENT_SAFELIST);
```

### 第二道防线：CSP HTTP 头配置建议

即使前端 DOMPurify 能够防范 XSS，配置 CSP（内容安全策略）HTTP 头作为**纵深防御**仍然是非常有价值的：

```nginx
# Nginx 配置示例
add_header Content-Security-Policy "
  default-src 'self';
  script-src 'self' 'unsafe-inline' https://www.recaptcha.net;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  img-src 'self' data: https:;
  font-src 'self' https://fonts.gstatic.com;
  connect-src 'self';
  frame-src 'self' https://www.recaptcha.net;
  object-src 'none';
  base-uri 'self';
  form-action 'self';
" always;
```

```apache
# Apache 配置示例
Header always set Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' https://www.recaptcha.net; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; img-src 'self' data: https:; font-src 'self' https://fonts.gstatic.com; connect-src 'self'; frame-src 'self' https://www.recaptcha.net; object-src 'none'; base-uri 'self'; form-action 'self'"
```

**CSP 提供的额外保护：**
- 即使 DOMPurify 出现漏洞（概率极低），`script-src` 限制可以阻止内联脚本执行
- `object-src 'none'` 禁止 Flash/Java 插件
- `base-uri 'self'` 防止 `<base>` 标签劫持
